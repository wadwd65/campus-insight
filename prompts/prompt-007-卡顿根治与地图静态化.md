## 三、AI 的回应摘要（技术链条）

### 3.1 卡顿：三次判断，前两次都不完整

| 轮次 | AI 的判断 | 处理 | 结果 |
|---|---|---|---|
| 1 | 入口页多层 `backdrop-filter` 吊打 GPU | 先去掉主面板实时模糊、粒子降配 | 主界面**不卡了**，但 3D 图还卡 |
| 2 | 269 万三角形 + 每帧重算 8192² 阴影 | 阴影降 4096 + 一次渲染；pixelRatio 1 | 帧时间 25ms→8ms，但仍不彻底 |
| 3 | **用户点破"内存没炸也卡"** → 查 GPU 进程归属 | 发现 `nvidia-smi` 里根本没有 msedge | 判定=浏览器**软渲染**（硬件加速被关） |

**关键诊断动作**（这一步是转折点）：

```
nvidia-smi --query-compute-apps=pid,process_name --format=csv
⇒ 列表里全是系统进程 + Wallpaper Engine，唯独没有 msedge
⇒ 结论：用户的外部浏览器压根没在用 GPU ⇒ 所有动画/WebGL 都在软件渲染
```

### 3.2 地图：从"实时渲染"彻底换成"预渲染静态图"

用户的直觉直接给了答案：**「要不直接做成静态图吧」「可以放大的静态图」**。

关键洞察：**2.5D 视角本来就是锁死不旋转的** —— 既然如此，根本不需要每帧实时渲染 269 万个三角形。落地：

```js
// 1. 相机定 2.5D 视角 → 离屏预渲染一张长边 3840 的高清图
// 2. toBlob 异步编码（同步 toDataURL 会阻塞主线程几十秒）
// 3. 渲染完销毁整个 WebGL 场景
scene.traverse(o => { o.geometry.dispose(); ...texture.dispose(); });
renderer.dispose(); renderer.forceContextLoss();
// 4. 之后拖拽/缩放 = 操作一张图（CSS transform，零 GPU 渲染）
```

内存从 **2~3GB → 一张几 MB 的图**。

### 3.3 立绘：本机 SD WebUI API 批量生成

链路：`127.0.0.1:7860` + anything-v5 → 随机 10 张 → 挑 → img2img 迭代 → extras 接口 R-ESRGAN 放大到 1536×2048。

## 四、我发现的问题 / AI 的自我修正

### 4.1 ★★★ 内存爆 ≠ 唯一瓶颈，要分开查

第 1 轮 AI 只查了 GPU 渲染开销，没查内存。**用户自己先看出来"内存占满 CPU 也满"**。实测 WorkBuddy 6.7G + msedge 3.77G = 10.5G，物理内存顶满 → 磁盘交换 → 全局卡。

**但更关键的是第二层**：用户后来报"内存没炸也卡"—— 这时候才发现真凶是**软渲染**。两次判断指向完全不同的原因。

### 4.2 ★★★ `backdrop-filter` 在动态背景上 = 帧数杀手

参考视频（B站二次元博客）的毛玻璃很漂亮，AI 第一版直接照搬 —— **但参考站的背景是静态图**，我们入口页背景是持续漂移的场景图 + 粒子。

```
backdrop-filter 的本质 = 对"元素背后的内容"实时模糊
背后内容每帧在动 ⇒ 浏览器每帧都要对每一层重做一遍全区域模糊
```

⇒ 去掉入口页所有 `backdrop-filter`，改"假玻璃"（半透明底 + 内高光 + 圆角），玻璃感仍在、逐帧模糊归零。

### 4.3 ★★★ 3D 场景的 rAF 循环必须"按需渲染"

`batLoop()` 是无限 `requestAnimationFrame`，**地图静止也每帧重绘全部**。改成 `if (!__IDLE_PAUSE || __DIRTY) render` —— 静止零渲染，交互才画。

### 4.4 ★★★ 大图导出必须用 `toBlob`（这条最坑）

调取景时页面反复假死，排查半天：**`toDataURL` 是同步 JPEG 编码**，3840 长边的大图在内存紧张时**阻塞主线程 60 秒以上**，导致 CDP 全部超时、页面假死，一度被误判成"死循环"。

⇒ 改 `toBlob`（浏览器后台线程异步编码）。**大图导出永远别用 toDataURL。**

### 4.5 验证方法本身会骗人（rAF 假绿）

用"rAF 计数静止不涨"验证按需渲染 —— 结果是**假阳性**：页面在后台时 rAF 被浏览器节流到 0，计数当然不涨。**测真实帧时间必须用 `renderer.render() + canvas.toDataURL()`（强制 GPU 同步完成），不能靠 rAF 计数。**

### 4.6 ★★★ 立绘：词条越少，本地模型反而发挥越好

AI 第一版给了一堆约束（`cel shading + flat coloring + clean lineart + 纯灰底`），出的是**古早平涂风**（模型最不擅长的方向）。用户一句 **「直接词条少给他按点，让他自由发挥吧」**，砍到只剩 `1girl, solo, full body, plain gray background` —— 画风质感**立刻跃升**（用上了光影、渐变、层次）。

### 4.7 立绘：裙子/腿/背景三个连环坑

| 现象 | 根因 | 修法 |
|---|---|---|
| 腿比例拉长、脚部畸变 | 抬腿 + 飘裙的复杂姿势，AI 画崩 | 加 `correct legs/feet` + NEG `bad legs`；姿势改站直 |
| 裙子"很怪"（乱飘布团） | 多层荷叶蕾丝 + 动态姿势 | **简化裙型 + 站直** |
| 背景跑偏（黑/紫/光环） | prompt 砍太狠后 `plain gray background` 被忽略 | 把灰底 tag **提到最前**（权重最高）+ NEG 排黑/紫/彩色底 |
| 8 张一个模子脸 | 同模型自带默认脸 | 换模型（SDXL base / Anything-V3）—— 但 SDXL base 出线稿（非动漫模型） |

### 4.8 参赛约束：端庄不暴露

用户明确：**「要参赛了所以还是暴露少一点，我们要做的好看一点，但是不要太暴露了」**。AI 画的裙 8 张里常有高开叉/短裙（二次元训练数据大量如此），要压住得专门强化 `knee-length / covered legs / modest` + NEG 排 `short skirt / high slit`。

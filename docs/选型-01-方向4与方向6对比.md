## 一、方向 6 · 校园 / 垂直社区全栈 MVP（数据看板）

### 官方原文怎么说的

> 基于标准数据格式（CSV/JSON）或公开 API 的智能分析系统。选手通过 AI 快速搭建精美的 ECharts/D3 动态图表大盘，并用大模型对长尾数据进行趣味解读。如个人消费账单「赛博算命」看板、GitHub 开源项目「情绪与舆情晴雨表」等。

### 做成什么产品（具体化）

**一句话**：上传一份消费明细表，页面自动出图表，再让 AI 用人话解读"你这个月钱花哪了"。

- **痛点**：大学生记了账也看不懂——数字躺在那，不知道问题出在哪
- **目标用户**：自己（有真实数据），以及任何有账单表的人
- **场景来源**：官方原文就举了「个人消费账单赛博算命看板」这个例子，直接踩在推荐范围内

### 用户看到的操作链

```
打开页面 → 拖入一份 CSV（或点"用示例数据"）
        → 页面自动出 3-4 张图表（分类占比 / 月度趋势 / 时段分布）
        → 切换筛选、悬停看细节
        → 点「求解读」→ AI 逐字流式吐出一段人话分析
```

### 界面上有什么

单页应用，从上到下三块：

1. **数据源区** —— 拖拽上传框 / 内置示例按钮 / 当前文件名
2. **图表区** —— 3-4 张卡片，每张一个 ECharts 图
3. **解读区** —— 一个"求解读"按钮 + 流式输出的文字面板

### 要写的代码是哪几块（技术名词 + 人话）

| 模块 | 技术 | 人话解释 |
|---|---|---|
| 数据读取 | PapaParse | 把 CSV 那堆文字，变成程序能算的表格 |
| 数据计算 | 原生 JS | 求和、分组、算百分比（≈ pandas 的 groupby） |
| 图表渲染 | ECharts | 把算好的数字变成柱状图、饼图 |
| AI 解读 | OpenAI 兼容接口 + SSE | 把算好的摘要发给大模型，让文字一个字一个字冒出来 |
| 界面 | React + Tailwind | 页面的骨架和长相 |

**共 5 块，其中 4 块都是纯前端，不碰服务器、不碰数据库。**

### 80 天怎么分（按 11-18 截止倒推）

| 阶段 | 做什么 |
|---|---|
| 第 1-3 周 | 数据层：读取 CSV、字段识别、算统计量、异常值处理 |
| 第 4-5 周 | 图表层：3-4 种图、筛选交互、悬停详情 |
| 第 6-7 周 | 解读层：接口封装、流式输出、失败重试、超时提示 |
| 第 8 周 | 打磨：空数据状态、加载状态、错误提示、界面统一 |
| 第 9-10 周 | 材料：README 复现指南、演示视频、技术文档 |

### 评委打开时会看到什么

一个能跑起来、能上传自己的表、能出图、能看解读的完整网页。功能不算惊艳，但**闭环是完整的**。

### 风险与退路

| 风险 | 退路 |
|---|---|
| 大模型接口调不通 | 退成"图表 + 固定模板文案"，产品照样完整 |
| 流式输出做不出来 | 退成一次性返回，功能不受影响 |
| 时间不够 | 砍掉解读模块，退成纯图表工具，仍然是一个可交付产品 |

**三个风险，每一个都有退路，且退到最后仍是完整产品。**

## 二、方向 4 · 低代码与智能表单生成引擎

### 官方原文怎么说的

> 探索人类用自然语言描述需求，由系统动态渲染生成可用工具的交互范式。如根据教师大纲「自适应生成含 LaTeX 公式考卷」的评测系统、根据企业表单需求一键动态生成全栈收集页面的微型平台。

### 做成什么产品（具体化）

**一句话**：你用一句话描述"我要一张什么表单"，系统现场把这张表单造出来。

- **痛点**：做一张收集表单要么学工具、要么找人做
- **场景来源**：官方原文两个例子——考卷生成、动态收集页

### 用户看到的操作链

```
左边输入框写一句话："我要一张收集班级同学暑期实习信息的表，含姓名、学号、公司、岗位、起止时间"
    → AI 返回一份「结构说明书」（一段严格格式的描述）
    → 系统照着它，右边现场渲染出一张真表单
    → 用户填写 → 导出成表格
```

### 界面上有什么

左右分栏：左边是需求输入区 + 生成按钮，右边是实时预览区。

### 要写的代码是哪几块

| 模块 | 技术 | 人话解释 |
|---|---|---|
| 需求输入 | React 表单 | 一个输入框加一个按钮 |
| AI 结构化输出 | OpenAI 兼容接口 | 关键：要求大模型**不许说人话，只许返回规定格式的结构** |
| 格式校验 | Zod | 检查 AI 返回的结构是不是符合预期，不合就报错 |
| 动态渲染 | React 条件渲染 | 按结构里的字段类型，渲染出输入框 / 下拉框 / 日期选择 |
| 公式渲染 | KaTeX | 如果做考卷方向，还要渲染数学公式 |
| 导出 | 原生 JS | 把填好的数据导成表格 |

**共 5-6 块，比方向 6 多一层，而且多出来的那层是最难的一层。**

### 风险与退路

| 风险 | 退路 |
|---|---|
| AI 返回的结构不合法 | **没有退路**——不合法就没有内容可渲染，页面是白的 |
| 字段类型识别错误 | 生成出来的是残缺表单，需要逐个字段调试 |
| 公式渲染有问题 | 考卷方向核心功能缺失 |

**核心模块一旦失效，产品直接归零。**

## 三、真正的分水岭（这部分最重要）

### 1. 大模型的角色完全不同

| | 方向 6 | 方向 4 |
|---|---|---|
| 大模型负责 | 写**一段解读文字** | 生成**整个页面结构** |
| 输出错了会怎样 | 文字不好看，图表照常 | 页面渲染失败，白屏 |
| 输出自由度 | 自由文本，随便写 | 必须严格符合格式，差一个括号就废 |
| 技术上的定位 | **装饰件** | **承重墙** |

同样是"用大模型"，一个是锦上添花，一个是命悬一线。

### 2. 出问题时你手里有没有"抓手"

这一点对新手是**决定性的**，值得单独讲。

**方向 6 的 bug 是确定性的**：图表没出来 → 控制台有红色报错 → 复制粘贴给 AI → 大概率一次修好。

**方向 4 的 bug 有一大半是概率性的**：同一句需求，这次生成的格式合法，下次不合法。你遇到的现场是——

> "有时候能出来，有时候出不来。"

这句话是没法直接贴给 AI 的。你没有报错可复制，只能自己描述"什么时候行、什么时候不行"。而对一个刚接触前端的人，**判断"什么时候行"本身就需要经验**。

想一想：你用 Python 那一个月，靠的是"出错 → 拿到报错 → 搜索 → 改 → 通过"这个循环。
方向 6 完整保留了这个循环。
方向 4 里，你有一半时间**拿不到报错**。

这不是难度问题，是**反馈信号的有无**问题。没有反馈，再努力也是在原地打转。

### 3. 退路长度

- 方向 6：满配 → 图表 + 模板文案 → 纯图表工具。**三级台阶，每级都还是能交付的产品。**
- 方向 4：满配 → 白屏。**一级台阶，下一步是空的。**

赛事评审里「过程可复现性」25% +「解题有效性」25% = 50% 的分，都建立在"**评委能把它跑起来、并看到它确实解决了问题**"之上。

一个功能朴素但跑得动的数据看板，这 50 分拿得住。
一个想法很酷但页面点不开的生成器，这 50 分同时失分。

## 四、决定

**方向 6。** 具体化为「**消费明细分析看板**」。

如果第 6-7 周发现大模型接口这关过不去，就按既定退路砍成纯图表工具，仍然是完整交付；把省下的时间全部投到 README 复现指南和演示视频上——那两项占 50% 的分。

## 一、产品定义

**一句话**：上传每日学习记录，出来几张图表，大模型诊断你的学习模式。

**它解决什么问题**：备考的人只知道「我学了多久」，不知道「我学得有没有用」。时长和正确率是两个维度，分开看都没问题，**交叉起来才看得出背离**——课时长最长的那科，正确率可能最低。这个结论人不主动算就看不见。

**范围护栏（明确不做）**

| 不做 | 原因 |
|---|---|
| 登录 / 账号体系 | 无后端，做了只会增加跑不起来的地方 |
| 数据库 / 云端存储 | 数据只在浏览器内存里，刷新即清空（README 里写清） |
| 后端服务 / 服务器部署 | 评委 clone 后 `npm run dev` 必须能跑，多一个服务就多一个失败点 |
| 移动端原生 / PWA | 只做响应式适配 |
| 真实用户数据收集 | 示例数据为模拟生成，README 声明 |

## 二、数据契约（全项目的锚点）

**文件格式**：UTF-8 编码的 CSV，首行为表头。

**字段定义（6 列，顺序可换，按表头名识别）**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `日期` | 日期 | 是 | `YYYY-MM-DD` |
| `开始时间` | 时间 | 是 | `HH:MM`，24 小时制。用于推导时段 |
| `科目` | 文本 | 是 | 自由文本，如 数学 / 英语 / 专业课 |
| `时长_分钟` | 整数 | 是 | 本次学习时长，正数 |
| `完成题量` | 整数 | 是 | 本次完成题目数，正数 |
| `正确数` | 整数 | 是 | ≤ 完成题量 |

**示例行**

```csv
日期,开始时间,科目,时长_分钟,完成题量,正确数
2026-03-01,08:30,数学,90,20,13
2026-03-01,14:00,数学,60,10,6
2026-03-01,20:00,英语,45,30,24
```

**粒度**：**一次学习会话一行**（不是一天一行）。一天可以有多次记录，也允许某天完全没有记录。

**程序派生的字段（不写进 CSV，由代码算）**

| 派生字段 | 算法 |
|---|---|
| `正确率` | `正确数 / 完成题量` |
| `时段` | 开始时间 < 12:00 → 上午；12:00 ~ 17:59 → 下午；≥ 18:00 → 晚上 |
| `日均时长` | 总时长 / 有记录的天数（**不是 / 日历天数**） |

## 三、示例数据必须讲清的四个故事 ⚠️

这是方向 C **最大的技术风险**。如果示例数据是随手编的，大模型只能说出「数学时间最多」这种废话，整个产品的加分点就没了。

示例数据必须是**人工构造的、逻辑自洽的**，让下面四件事在数据里真实存在（不是靠文案硬说）：

| # | 要存在的事实 | 大模型据此能说出的话 |
|---|---|---|
| 1 | 数学时长占比最高（约 45%），但正确率最低（约 62%） | 「数学占了 45% 的时间，正确率却最低」——**投入产出背离** |
| 2 | 英语正确率在某个时间点起连续下滑约 11 个百分点，且下滑起点与数学时长上升同步 | 「英语正确率从 X 日起下滑 11 个百分点，与数学加时同步」 |
| 3 | 上午正确率明显高于下午（约 78% vs 62%） | 「你的高效时段是上午，但数学被排在下午居多」 |
| 4 | 至少一个反例：某科目时长在涨、正确率也在涨 | 说明数据不是一条直线，避免结论过于顺拐 |

**验收标准**：用这四句话去问大模型，它必须能从统计摘要里得出**至少 3 条**，且每条都带具体数字。做不到就回去重造数据。

## 2026-10-23 · v30 问卷 × 行动地图贯通（进行中）

评审反馈「测评单调」。实际走查后发现**不是功能少**：两条线本来就共用一本账 ——
`useGameStore.applyChoice` 同时接收问卷每题的增量和地图每一步的增量，
`ReportView` 也已经有「安排我的校园一天 →」（`onGoMap`）和「回到地图」（`onBackToMap`）两个出口。

真正缺的是三处「看不见 / 接不上」：

1. **入口页的行动地图入口藏在 `<details class="landing-explore">` 折叠区里**，默认收起。
   而 `.landing-actions` 的 CSS 早就写着 `grid-template-columns: 1.25fr 1fr 1fr`
   —— **编排了三列，只放了两个按钮，第三格空着**。布局为它预留了位置，按钮却没加进去。
2. **一天固定 4 个时段**（`mapPlaces.js` 的 `SLOTS_PER_DAY = 4`），与问卷算出的体力无关。
3. **地图页只显示「本次属性增量」**，看不到「我现在是什么属性」。

本轮改动：

- `components/LandingContent.jsx`：入口页补第三个按钮「行动地图 / ACTION MAP」，
  与「一起填报」「自己体验」并列（三列布局现成，无需改 CSS）
- `store/useGameStore.js`：新增 `slotsPerDay`（默认 4）与 `setSlotsPerDay`（夹紧 3~6）
- `lib/campusJourney.js`：
  - `buildCampusJourney(trail, slotsPerDay = SLOTS_PER_DAY)` 支持动态时段，返回值增加 `slotsPerDay`
  - 新增 `slotsForPercents(percents)`：`sport ≥ 65` 给 5 个时段、`≤ 35` 给 3 个、其余 4 个；无问卷数据返回 `null`
  - `buildJourneyText` 改为读 `journey.slotsPerDay`

**为什么用 percent 而不是账本值做阈值**：账本是不夹紧的累加数（可正可负、无固定上限，
原因见 store 注释），拿它当阈值会随「去过几个地点」而漂移；`percent` 是相对基准人群算出来的，稳定在 0~100。

**验证（已跑，结果如下）**：

- 相关测试全绿：`selftest` 124 项 / `selftest:store` 39 项 / `selftest:map` 54 项 /
  `smoke:csv` 30 项 / `test:journey` 8 项 / `test:answers` 10 项 / `test:experience` 20 项 —— **合计 285 项通过**
- `slotsForPercents` 边界值 **9/9 通过**（65→5、64→4、36→4、35→3、无数据→null）
- 动态时段：传 5 得 5 格、传 3 得 3 格、不传得 4 格
- 构建通过（`vite build` 910ms）
- 浏览器实测：入口页 `.landing-actions` 渲染 **3 个按钮**，
  网格 `408.75px 340.625px 340.625px`（1.2:1:1）

**过程中修掉的一个真实冲突**：`product-unity.css:36` 用
`.landing-page .landing-actions { grid-template-columns:1.15fr 1fr }` 覆盖了 `landing.css` 的三列规则
（选择器多一个类，优先级更高），导致第三个按钮被挤到第二行。已改为 `1.2fr 1fr 1fr`。

**⚠️ 未跑的一项**：`test:runtime`（3D 地图运行时）当前失败，但**与本次改动无关** ——
它测的是 `map-src/web/campus-walk.js` 等文件，而那几个文件在 18:57~19:03 正被另一路修改（现在 19:04）。
等对方收工后需复跑一次 `npm run check` 全量确认。

## 2026-10-26 · 复现第三个发现：dist/index.html 的行尾会在克隆后分叉

**现象**：在克隆出来的目录里跑完 `npm run build`，`git status` 会多出一条
` M dist/index.html`。原仓库里同样跑 build 却始终干净。

**根因（逐字节定位）**

| 位置 | 行尾 | 产物大小 |
|---|---|---|
| 原仓库源 `index.html` | **21 个 CRLF**（历史遗留） | — |
| 克隆后源 `index.html` | **0 个 CRLF**（被 `.gitattributes` 的 `* text=auto eol=lf` 转成 LF） | — |
| 原仓库构建产物 | CRLF | 1687 字节 |
| 克隆后构建产物 | LF | 1666 字节 |

差额正好 21 字节 = 21 个 CR。Vite 会继承源 `index.html` 的行尾，
所以「源是什么行尾，产物就是什么行尾」。仓库里提交的是 CRLF 产物，
评委克隆后源变 LF、产物也变 LF ⇒ 与索引不一致 ⇒ 报 M。

**影响**：功能零影响（HTML 行尾等价），也不影响部署包 —— 仓库 `dist/` 与
`release-download/` 两个 zip 目前**互相一致**（都是 CRLF 版）。
唯一后果是评委构建后看到一处脏文件，可能误以为「构建不可复现」。

**已采用方案 3（2026-10-26 用户决定）：只在 README 写「已知现象」。** 三种候选与结论：

1. 源转 LF + 重打两个部署包（约 75 MB 需重新生成）—— 最彻底，但要重建发布物并重验哈希
   ⇒ **未采用**，改造成本高于它解决的问题
2. `.gitattributes` 把源 `index.html` 固定为 CRLF（`index.html text eol=crlf`）—— 改动最小，
   仓库/产物/部署包三者继续一致；代价是 HTML 用 CRLF 不合 Web 惯例 ⇒ **未采用**
3. **只在 README 写「已知现象」—— 已执行**（`390e0ad`）：第 4 步启动处加一句短提示，
   文末「验证与已知限制」加对比表 + 两种可自证的判断方法

**判据（实测，写进 README 前自己先验过）**：把仓库版与构建版的 `CR` 全部去掉后
比对，内容哈希**完全相同**（`15bcb43e…`）⇒ 确认只有空白字符差异，没有文字改动。
注意 `--ignore-cr-at-eol` 之后**仍会剩 1 行**：`<div id="root"></div>` 那一行在仓库版里是
`\r\r\n`（两个 CR），所以单靠这个参数判不干净，得用「去 CR 后哈希」才严密。

**结论**：这是「构建产物入库」带来的副作用，不影响任何功能。
若评委直接解压 `release-download/` 里的包，完全不受影响；只有「先 clone 再自己 build」才会碰到。

### 真凶一：浏览器启发式缓存（用户反馈「没有」）

### 2026-10-27 夜 · 真正的解法：改默认机位，而不是继续堆细节

`fit()` 里 `distance: fitDistance(aspect)` 是"把整个校区塞进视口"，实测约 **1.2 px/m**。

改动：`distance × 0.72`、`elevation 1.08 → 1.0`（俯角压低，多看立面少看屋顶）。
每栋楼占屏 **+38%**，约 1.7 px/m。

**代价与取舍**：默认视角不再包含完整校区（可用「俯瞰核对」或缩小按钮退回）。
这是"要么看全、要么看细"的二选一 —— 之前几轮一直在"看全"的前提下加细节，所以怎么加都读不出来。

### 2026-10-27 深夜 2 · 湖面白雾的真因（对照实验定案）

湖左半边一直有一片柔和白雾，先怀疑贴图，改了 `waterTexture` 的边缘色（`#a5b59a` → `#7e9880`）——
**没变**。于是做对照实验：把 `specular` 临时设为 `0x000000`，白雾**完全消失**。

⇒ 真因是 **Phong 高光**：湖面是一整块约 150 米见方的平面，
`shininess 130 / specular 0xa8c0cc` 的高光叶瓣在这样的尺度上不是"一个小亮点"，
而是"扫过半个湖的一片白"。中途试过 `0x3b4a4f` + `shininess 240`，仍有明显白雾。

**结论：大平面不要用 Phong 高光做水面反光**，它无法收敛成合理的高光形状。
最终 `specular: 0x000000`。若以后要水面反光，正确做法是贴图级的 glitter
或用环境贴图反射，而不是指望材质高光。

### 2026-10-28 · 「树加不上去」的真因：函数内部有 132 的硬上限

昨天以为是随机撒点饱和，**判断错了**。真因在 `plant()` 里：

```js

```

`planted.length>=132` 是**函数内部的硬上限**。我前一天把外层循环的上限从 210 调到 320、又加了一层 560 株灌丛，

改法（三处）：
1. 上限 `132 → 380`
2. `canPlant(x,z,spacing=9)`：间距从写死 9 米改成可传参
3. 灌丛层传 `spacing=4.5`，小灌木才能挨着长

| 项 | 改前 | 改后 |
|---|---|---|
| 三角形 | 1,275,062 | **1,793,438**（+518k，+41%） |
| 实例数 | ~2.5k | **6,525** |

**教训**：调参数前先确认"这个参数是不是真的被读到"。

### 2026-10-28 · 坐标系错配：每栋楼旁边那堆白色碎片的真因

用户指出"每个房子旁边都是这个奇怪的形状，多出来一堆东西"。

**真因在 `wing()` 的两套坐标系**：

```js
体块本体：add(..., Math.min(w,d), h, Math.max(w,d), angle)   // angle = p.rotation (+90° if w>d)
屋顶/檐口/女儿墙/skin：add(..., w, d, p.rotation)            // 另一套！
```

当 `w>d`（比如教学楼 36×10）时，体块被转了 90°，而屋顶板、檐口、女儿墙、墙垛
仍按原来的 w/d 方向摆放 —— 于是一半构件飞到楼体外面，形成每栋楼两侧的白色刀片。
**这个错配在原始代码里就存在**（屋顶板一直这么写），我后来加的 `parapet` / `skin`
只是把它放大到无法忽视。

**改法**：全部统一到"体块自身坐标"——先算 `bw=min(w,d)`、`bd=max(w,d)`，
所有子构件都用 `(bw, bd, angle)`；`skin()` 改为接收 `(bw,bd,rot)`，
墙垛沿 bd 方向排、贴在 ±bw/2 上。

顺带删掉了四角壁柱（同样是按 w/d 摆的，本来就在楼外）。

核对：三角形 1,817,958 → 1,820,610，0 报错，白色碎片消失。

### 2026-11-08 十四改（v19）：道路系统整体重构

> 用户：补丁式修补每次都「修一个冒一个、修完把以前修好的又弄回去」，**要求直接重构所有马路**；并明确批评此前一直以车内视角为准，**必须以第一人称步行视角为准**，第三人称俯视也能看到所有路线的裂纹与冲突点。

**一、根因（为什么补丁必然失败）**

旧实现是「每段一个 `box:road` / `box:sidewalk` 实例」：
- 端点加长（`length+.6`）⇒ 相邻段水平重叠、顶面同高 ⇒ **z-fighting 冲突点**（移动时闪）＋重叠段垂直侧面背光发黑（裂片）。
- 端点精确相接（`length`）⇒ 斜向拐角两段矩形只在中心线相交 ⇒ **三角缝隙/裂纹**。
- 补盖板/方块 ⇒ 不同高度或不同 UV 的独立面 ⇒ 色块/断层；补块尺寸失控 ⇒ 全局污染。

**这三种状态互相排斥，靠调端点距离不可能同时满足**，所以必须换模型。

**二、重构方案（不再有「段拼接」这回事）**

- 删除整段旧的 `data.roads.forEach(...add('box'...))`、全部 junction 补块逻辑与历史注释。

  - 每个拐点用 miter `sc = halfW / max(.35, dot(n, n2))` 算左右边界（`n` 为两段法线角平分线），上下限都钳制；
  - 相邻段**共用同一组顶点**（topology 连续）⇒ 物理上零重叠、零缝隙；

- 闭合环路（road#0）自动首尾闭合，四个大转角由 miter 顶点自然过渡。

### 2026-11-08 十五改（v23 当前交付）：路网改为单张覆盖纹理 + 单一平面

> 用户：第三人称就能看到很多公路变形、重复、交切处闪烁；批评此前一直以车内视角为准。

- 结论：只要还是「多段 / 多 Mesh 拼起来」，这三个问题就绕不开。

**二、最终方案：取消「拼接」这个概念**

- `patch-v20`：删除全部 `box` 段 / ribbon / junction 补块逻辑。改用 **canvas 2D 把整张路网一次画完**：

### 2026-11-08 十七改（v25 当前交付）：恢复渲染精度

> 用户：渲染精度非常低，稍远一点的物品就一片糊。中途一度以为「改错文件 / 树和地图变形」，经核对是**刷新撞上旧版本缓存**，非文件被改；两版全景真读树/道路/建筑/操场/湖形状位置完全一致，桌面唯一版时间戳一直是 14:47 的 v24。

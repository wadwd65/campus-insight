## 为什么没有把原有后端直接搬到 Sites

Sites 运行时为 Cloudflare Workers，当前完整服务依赖 Node 原生 HTTP、`node:sqlite`、私有文件和 scrypt。发布前端资源不会使这些模块自动运行。若未来改用 Workers，需要另做数据库、事务与身份适配，并完整验证权限，不能以静态页面上线代替后台验收。

本轮还尝试了隔离数据的临时公网通道。官方 cloudflared 下载和空通道创建成功，但完整测试服务的启动被自动审批拒绝，只返回 `blocked by policy`。已停止所创建的通道，没有改用其他命令绕过该限制，也没有把本机真实账号数据接到公网。此项不计作完整公网验收通过。

## 给下一位部署者的具体交接

1. 使用同版 `campus-insight-admin.zip`，不要只上传 `dist`。包内含 Node 服务、配置启动工具、HTTPS 模板和备份恢复说明；不含本机密钥、初始化口令或真实数据库。
2. 选择能持续运行 Node.js 24.21+ 并提供私有持久磁盘的服务器。普通静态网站空间不适合在线收卷。已有 Docker 服务器可使用包内 `deploy/compose.yaml` 与 Caddy。
3. 从 `.env.example` 准备服务器自己的 `.env.local`。设置正式 HTTPS `APP_ORIGIN`、站点名称、`CAMPUS_DEPLOYMENT=shared` 或 `self-hosted`；数据必须放在公开资源目录之外。
4. Docker 方案把 `CAMPUS_DOMAIN` 配为自己的域名，将域名解析到服务器，并确保 HTTPS 所需端口可用。启动命令为 `docker compose --env-file .env.local -f deploy/compose.yaml up -d --build`。普通 Node 方案按随包的启动说明执行。
5. 首次启动自动生成服务器私有 `setup-key.txt`。只有站点维护者读取它并完成首次开通；不要公开它，也不要把默认管理员密码写进代码。成员使用邀请码注册，密码为 6～12 位。
6. 一个浏览器登录管理员建圈并生成邀请；另一个浏览器作为普通成员打开邀请、注册、答完十题、核对同意并提交。返回管理员刷新，核对收到的答案、时间及导出文件。
7. 重启服务后重新登录，确认圈子和答卷仍存在；再验证跨圈隔离、成员无法看他人答卷、撤回和备份恢复。正式收集真实资料之前，要完成这些外网检查。

还需要部署者提供或登录云平台账号，并确定服务器、持久磁盘和域名。本轮没有购买服务，也没有创建需要接受平台协议的云账号。具备这些条件后，无需重写前端即可继续部署当前 Node 服务。
